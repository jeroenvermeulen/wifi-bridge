# wifi-bridge

> [!WARNING]
> Disclaimer: most of this repository was generated by AI, but tested by humans. 

Firmware that turns a cheap ESP32 + W5500 (or W5100) board into a transparent WiFi-to-Ethernet bridge
for one wired device. The device behaves as if it were on the WiFi network itself: it gets its
IP address from the WiFi network's router, and other hosts can reach it directly.

Supported boards, one PlatformIO environment each:

| Environment | Board | Hardware docs |
|---|---|---|
| `esp32-s3-poe` (default) | AliExpress "ESP32-S3 PoE W5500 N16R8" development board | [esp32-s3-poe-w5500-n16r8-dev-board](https://github.com/jeroenvermeulen/esp32-s3-poe-w5500-n16r8-dev-board) |
| `lolin-s2-mini` | WEMOS LOLIN S2 Mini wired to a W5500 module (USR-ES1) | [esp32-w5500](https://github.com/jeroenvermeulen/esp32-w5500) |
| `esp32-uno-shield` | ESP32-WROOM-32U wired to an Arduino Uno Ethernet Shield (W5100) | [below](#esp32--arduino-ethernet-shield-notes) |
| `esp32-w5500` | ESP32-WROOM-32U wired to a W5500 module (USR-ES1) | [below](#esp32--w5500-module-notes) |

## How it works

- The bridge learns the wired device's MAC address from the frames the device sends. It doesn't
  store it: a bridge powered up without its device stays off WiFi, instead of joining as a device
  that may be somewhere else.
- It joins the WiFi network as a station *using that MAC address* (MAC cloning). WiFi client
  mode can only carry one MAC address, which is why this supports a single device.
- On networks with several access points it joins the strongest one. If the signal drops below
  -75 dBm, it scans once a minute and moves to an AP that is at least 10 dB stronger. Joining
  the first AP found instead once left the bridge at -86 dBm, with ~70 KB/s down and stalled
  uploads.
- Raw Ethernet frames are copied unchanged between the Ethernet chip and WiFi. The ESP32 has no IP
  address of its own.
- Frames from the wired device are dropped if their IPv4 header or TCP/UDP checksum is wrong, so
  TCP resends them. The W5500 occasionally delivers a frame that was corrupted after the wire
  (see the [esp32-w5500 notes](#esp32--w5500-module-notes)), and some of those reached servers.
- If a different device is plugged in, the bridge switches to its MAC once the old device has
  been silent for 10 seconds.
- It leaves WiFi when the device has been silent for 15 minutes, or the Ethernet link has been
  down for 10 seconds (W5500 boards; the W5100 can't see the link).
- **LAN guard**: if 4 or more different devices send on the Ethernet port within 10 seconds, the
  port is on a network, not on one device. The bridge then doesn't bridge and stays off WiFi
  until the port has been quiet for a minute. It waits 3 seconds after the first frame before
  cloning, so a network has time to show itself. Without this, it once cloned the MAC address of
  the router of the LAN it was plugged into.

## Performance

Measured through a Realtek USB 2.5G adapter on a Mac, to the internet over WiFi (-55 to -61 dBm):

| | `esp32-s3-poe` | `lolin-s2-mini` | `esp32-uno-shield` | `esp32-w5500` |
|---|---|---|---|---|
| Ethernet link | 10 Mbit full (autonegotiated) | 100 Mbit full (autonegotiated) | 100 Mbit full (autonegotiated) | 100 Mbit full (autonegotiated) |
| Download (WiFi → Ethernet) | ~700 KB/s | ~840 KB/s | ~220 KB/s | ~1.9-2.0 MB/s |
| Upload (Ethernet → WiFi) | ~1.0 MB/s | ~625 KB/s | ~130-150 KB/s | ~740 KB/s (5 MB) |
| Ping to the router | ~8-20 ms average, 0% loss | ~5.5 ms average, 0% loss | ~12 ms average, 0% loss | ~4-5 ms average, 0% loss |

The W5500 on the S3 board can't hold 100 Mbit. It autonegotiates, and the link flaps for ~15 s
until the Mac's adapter settles on 10 Mbit (S3 measured 2026-10-24 at -63 dBm). The W5500
module on the S2 Mini runs at 100 Mbit (measured 2026-10-24 at -44 dBm). There the limit is WiFi: the S2 Mini only transmits
reliably at reduced power (see below).

`esp32-w5500` numbers are from `tools/stress_test.sh` on 2026-10-26 (16 downloads and 16 uploads
of 5 MB, WiFi at -40 dBm, no failed transfers), after the transmit and receive changes to the
W5500 driver described [below](#w5500-driver-patch); before them it did ~1.4 MB/s down and
~670 KB/s up. The same internet connection does 11 MB/s down and 2.8 MB/s up from the Mac
directly. Eight parallel uploads shared ~0.9 MB/s evenly (2026-10-24). Uploads are limited by
the wired device's bursts, see the [W5500 module notes](#esp32--w5500-module-notes).

On `esp32-uno-shield` (WiFi at -43 dBm) the W5100's SPI is the limit: it moves one byte per
3.5 µs, about 280 KB/s at best, and a full-size frame takes ~5 ms each way.

## Setup

1. Install [PlatformIO](https://platformio.org/). ESP-IDF is downloaded on the first build.
2. Copy `src/wifi_credentials.example.h` to `src/wifi_credentials.h` and fill in your network.
   That file is gitignored.
3. Connect the board and flash it with its environment:
   ```
   pio run -e esp32-s3-poe -t upload
   pio run -e lolin-s2-mini -t upload
   pio run -e esp32-uno-shield -t upload
   pio run -e esp32-w5500 -t upload
   ```
   - ESP32-S3 PoE board: use the **ESP-USB** port with a **USB-A to USB-C** cable (USB-C to
     USB-C gives no power on this board), and switch it on.
   - LOLIN S2 Mini: the first time, put it in download mode (hold **0**, press **RST**, release
     **0**) and press **RST** after flashing. After that, uploads work without buttons.
4. Plug the device into the RJ45 port. **Never connect the RJ45 port to a network**, and
   certainly not the one the bridge's WiFi joins. The LAN guard (see above) should catch that,
   but a quiet network with fewer than 4 active devices can still look like one device.

## Configuration

Board settings live in `boards/<environment>.defaults`, an ESP-IDF sdkconfig fragment applied on
top of [sdkconfig.defaults](sdkconfig.defaults). The bridge's own options are declared in
[src/Kconfig.projbuild](src/Kconfig.projbuild):

| Option | Notes |
|---|---|
| `CONFIG_BRIDGE_ETH_W5500` / `_W5100` | Ethernet chip. |
| `CONFIG_BRIDGE_PIN_MOSI`, `_MISO`, `_SCLK`, `_CS` | SPI wiring. |
| `CONFIG_BRIDGE_PIN_INT` | Chip interrupt; `-1` polls instead, and keeps the W5500's INT output quiet. |
| `CONFIG_BRIDGE_PIN_RST` | Chip reset; `-1` if not connected. |
| `CONFIG_BRIDGE_PIN_LED_TX`, `_RX` | Activity LEDs, active high; `-1` for none. TX: frames out the Ethernet port. RX: frames in from it. |
| `CONFIG_BRIDGE_SPI_HOST_SPI2` / `_SPI3` | SPI host. SPI2 unless set; the ESP32's VSPI is SPI3. |
| `CONFIG_BRIDGE_SPI_MHZ` | SPI clock. Above 26 MHz the pins must be the IO_MUX pins of that SPI host. The W5100 is rated for 14 MHz. |
| `CONFIG_BRIDGE_ETH_AUTONEGOTIATE` | `n` forces the link mode below. W5500 only. |
| `CONFIG_BRIDGE_ETH_SPEED_10M` / `_100M` | Forced speed. |
| `CONFIG_BRIDGE_ETH_DUPLEX_HALF` / `_FULL` | Forced duplex. Must match the wired device: an autonegotiating device falls back to half duplex against a forced link. The Mac's USB adapter did, although macOS showed full duplex: forced full lost ~80% of the frames to it under two-way traffic, while single transfers looked fine. Forced half works, but sends often wait out the Mac's traffic (11% ping loss under load). Prefer autonegotiation. |
| `CONFIG_BRIDGE_WIFI_MAX_TX_POWER` | In 0.25 dBm units, `0` for the chip default. |

ESP-IDF only applies defaults to a new configuration, so after editing a defaults file delete
`sdkconfig.<environment>` (or change the option with `pio run -e <environment> -t menuconfig`).

To add a board, copy one of the files in [boards/](boards/) and add an environment to
[platformio.ini](platformio.ini) that points `board_build.cmake_extra_args` at it.

### LOLIN S2 Mini notes

- **WiFi TX power is capped at 8.5 dBm.** At full power, uploads crawled at ~75 KB/s with WiFi
  TX errors, and the USB console died under traffic. That fits supply dips on the board's small
  regulator, which also feeds the W5500 module. The cap made uploads 7× faster.
- **The console runs over TinyUSB** ([src/usb_console.c](src/usb_console.c)): the S2 has no
  USB-Serial/JTAG, and ESP-IDF's built-in USB CDC console stopped under traffic. The TinyUSB
  console handles PlatformIO's 1200 bps touch and esptool's DTR/RTS reset, so uploads don't need
  the buttons. Boot and panic messages go to UART0 (GPIO43), which isn't connected.
- **WiFi and LWIP buffers are in PSRAM**: the S2's internal RAM ran out under load.

### ESP32 + Arduino Ethernet Shield notes

Wiring: SCK GPIO14, MISO GPIO12, MOSI GPIO13 (the HSPI pins), CS GPIO5. The shield's INT and
RST are not connected. The console is the board's USB-serial chip, e.g. `/dev/cu.usbserial-0001`.
Opening that port resets the board, also with `tools/serial_log.py`.

- **The W5100 can't report the link state.** It has no PHY status register, so the bridge
  always shows `eth=up`, also with no cable.
- **It always autonegotiates**: the forced link mode options don't apply.
- **SPI is the bottleneck.** The W5100 moves one data byte per 4-byte SPI frame, with CS toggled
  in between, so a full-size Ethernet frame takes ~1500 SPI transactions, ~5 ms. The driver starts
  them through the SPI registers directly, at 3.5 µs per byte at 13.3 MHz. Through ESP-IDF's
  SPI helpers this was 4.0 µs.
- **MISO sampling**: with ESP-IDF's default timing every byte read from the shield came in shifted
  right by one bit. The driver sets `input_delay_ns` to 40 ns: a test of 64 KB per setting read
  back correctly from 25 to 70 ns and wrong at 0 to 20 ns.
- 16 MHz still read back correctly, 20 MHz corrupted 7% of bytes. The board stays at the W5100's
  rated 14 MHz (13.3 MHz in practice).

### ESP32 + W5500 module notes

Wiring: the VSPI pins, so SPI runs at 40 MHz. The HSPI pins would put MISO on GPIO12, which
selects 1.8 V flash when it is high at reset. The console is the board's USB-serial chip, as on
the Uno shield board. Measured with a USR-ES1 module; a blue AliExpress W5500 module was used first.

| W5500 | SCLK | MOSI | MISO | CS | RST | INT |
|---|---|---|---|---|---|---|
| ESP32 GPIO | 18 | 23 | 19 | 5 | 17 | 16 |

RST and INT stay off GPIO21/22 to keep the ESP32's usual I2C pins free.

Activity LEDs: green TX on GPIO25, yellow RX on GPIO26, each wired GPIO → 330 Ω → LED → GND
(about 4 mA). A deep green LED (~3 V forward voltage) needs about 100 Ω to be bright enough.

- **The INT wire can reset the W5500.** With the blue module, the W5500 reset itself 3 to 8
  times per 80 MB of uploads: every register back at its default and the link down for 2
  seconds. That kept happening when the firmware polled and ignored INT, and stopped when the
  chip's INT output was kept quiet: INT's edges coupled into the other wires, probably RST. The
  USR-ES1 had no resets in 80 MB with INT on. If a module does reset, set
  `CONFIG_BRIDGE_PIN_INT=-1`: the bridge then polls every 1 ms at the same throughput and keeps
  INT quiet.
- **Don't force 10 Mbit with the Mac's USB adapter.** At forced 10 Mbit full, ~80% of the frames
  from the bridge to the Mac were lost while the Mac was also sending, so parallel uploads (as
  speedtest.net does) stalled and reset. Forced half duplex works but loses 11% of pings under
  load. With autonegotiation nothing was lost. The S3 board had the same loss (~86%) until
  it was switched to autonegotiation.
- **Corrupted frames**: at 100 Mbit about 1 in 60000 frames from the wired device came out of
  the W5500 with a wrong TCP checksum, with both modules. The frames were fine on the wire
  (the Mac's adapter computes the checksums), and reading a known pattern from the W5500 during
  the same traffic gave no SPI errors. So the W5500 stores them corrupted. Some passed the
  network unchecked and failed uploads with a TLS "bad record mac" error (1 or 2 of every 16
  uploads of 5 MB). The bridge now drops them: 48 uploads, no errors.
- The SPI itself is clean: 600 MB read back without an error at 40 MHz with WiFi off, also with
  frame-sized lengths.
- **Uploads are limited by bursts from the wired device.** The W5500 holds 16 KB of received
  data and the ESP32 drains it at ~3.3 MB/s, but the Mac (TCP segmentation offload on) puts up
  to 64 KB on the 100 Mbit wire in 5 ms. The chip then drops frames without any counter showing
  it; only comparing the Mac's sent-frame count with the bridge's received count reveals it
  (~1.7% of upload frames). The resulting TCP loss keeps uploads at ~0.7 MB/s although the WiFi
  side forwards 2 MB/s of UDP. Pacing (`curl --limit-rate`) doesn't help, since each write is
  still a burst; a sender whose in-flight data is capped at 16 KB sees no loss but is then
  bound by the ~28 ms round trip through the bridge and the internet (~575 KB/s). The
  Ethernet PAUSE mechanism would be the fix, but the W5500 doesn't advertise it, so the Mac's
  adapter won't honor it.
- The driver recovers if the W5500 resets or its socket closes (see
  [below](#w5500-driver-patch)), so the bridge comes back after ~2 seconds instead of needing a
  power cycle.

## Monitoring

The bridge logs over USB serial every 10 seconds: link states, signal strength, frame counters
per direction, drops, free internal memory, CPU use per task, and the time per frame spent in
the Ethernet transmit and receive paths.

```
~/.platformio/penv/bin/python tools/serial_log.py [PORT]
```

This opens the port without resetting the board, unlike most serial monitors.
[tools/bridge_test.sh](tools/bridge_test.sh) runs a ping, download and upload test bound to the Mac
interface that is wired to the bridge (default `en20`). [tools/stress_test.sh](tools/stress_test.sh)
runs 16 downloads and 16 uploads of 5 MB with the board's log alongside and compares the Mac's
frame counters with the bridge's; faults that happen once per 10-20 MB only show up there.

## W5500 driver patch

[src/w5500/w5500_mac.c](src/w5500/w5500_mac.c) is a patched copy of the ESP-IDF 5.4.1 W5500 MAC
driver. Upstream stops waiting for "send complete" after about 10 SPI reads, which is before a
full-size frame has left a 10 Mbit wire. The next frame is then started mid-transmission and
lost, which cost about 35% of downloaded frames. The patched driver waits for as long as the frame
needs on the wire. It also polls the command register instead of sleeping 10 ms.

Other changes:

- "Send complete" is read once more after the wait deadline before a frame counts as failed.
  Before, a bridge task preempted past the deadline reported a sent frame as failed and left the
  flag set for the next frame, which then started the frame after it mid-transmission. On the
  single-core S2 that hit ~60 frames per 16 downloads of 5 MB.
- The socket status register is read at 0x0003. ESP-IDF's header has 0x0004 (Sn_PORT0, always 0
  in MACRAW mode); upstream never reads it, but the recovery below took every failed send for a
  closed socket and reopened it, which put the receive pointers out of step.
- If the W5500 resets itself, the driver restores its setup when the link comes back, or on the
  next failed send when the reset was too short for esp_eth to notice the link drop. Before,
  the chip stayed silent until a power cycle.
- A received frame length the chip can't produce means the read pointer is out of step with the
  frames. The driver then drops all received data and continues at the next frame. Upstream
  returned an error and its receive task spun on it until the watchdog fired.
- When polling (no INT pin), the chip's INT output stays quiet.
- Transmit no longer waits for the frame to leave the wire. The next frame is written into the
  chip's TX memory while the previous one is being sent, and "send complete" of the previous
  frame is checked just before the next SEND. Together with fewer register accesses per frame
  (the write pointer is tracked while a frame is in flight, the free size is implied, the SEND
  command isn't read back) a full-size frame went from ~650 µs to ~450 µs of the bridge task's
  time, and downloads on `esp32-w5500` from ~1.4 to ~1.9 MB/s.
- Receive reads everything the chip holds in one SPI transfer (up to 8 KB) and splits it into
  frames in RAM, instead of ~8 small SPI transactions per frame. The chip's 16 KB receive
  memory drains about 30% faster (~3.3 MB/s), which matters because the wired device may send
  at 100 Mbit in bursts (see the W5500 module notes).

## W5100 driver

[src/w5100/w5100.c](src/w5100/w5100.c) is a MAC and PHY driver for the W5100, which ESP-IDF
doesn't support. It is modeled on the W5500 driver and uses MACRAW on socket 0. On the W5100
that mode has no MAC filter, so it receives every frame on the wire. See the
[shield notes](#esp32--arduino-ethernet-shield-notes) for its SPI handling.
